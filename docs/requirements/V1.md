# QA Commerce Lab — Requisitos V1

## 1. Objetivo

O QA Commerce Lab é um e-commerce desenvolvido para estudo e prática de
Quality Assurance, testes de API, testes de banco de dados e automação E2E.

A aplicação deve possuir um comportamento funcional padrão e um Bug Lab,
no qual defeitos conhecidos podem ser habilitados individualmente para
execução de cenários de teste.

---

# 2. Produtos e catálogo

## RF-PROD-001 — Catálogo

O sistema deve listar somente produtos ativos.

## RF-PROD-002 — Dados do produto

Cada produto deve possuir:

- ID interno;
- SKU único;
- nome;
- descrição;
- preço;
- estoque;
- status ativo/inativo.

## RF-PROD-003 — Preço

O preço:

- é obrigatório;
- não pode ser negativo.

## RF-PROD-004 — Estoque

O estoque:

- é obrigatório;
- não pode ser negativo.

## RF-PROD-005 — Consulta individual

O usuário deve poder consultar um produto individualmente.

Produto inexistente deve retornar HTTP 404.

## RF-PROD-006 — Produto sem estoque

Produto sem estoque continua visível no catálogo, mas deve ser apresentado
como indisponível para compra.

## RF-PROD-007 — Busca parcial

A busca deve:

- localizar produtos utilizando parte do nome;
- procurar a sequência em qualquer parte do nome;
- ser case-insensitive;
- retornar somente produtos ativos.

Exemplo:

Produto: Notebook QA

Buscas válidas:

- notebook
- note
- book
- qa
- NOTE

## RF-PROD-008 — Autocomplete

O campo de busca deve apresentar sugestões durante a digitação.

Regras:

- iniciar a partir de 3 caracteres;
- utilizar busca parcial;
- ser case-insensitive;
- sugerir somente produtos ativos;
- utilizar debounce de 350 ms;
- atualizar sugestões conforme o usuário continua digitando.

# 3. Usuários

## RF-USER-001 — Cadastro

O cadastro deve solicitar:

- CPF;
- data de nascimento;
- nome completo;
- e-mail;
- senha;
- endereço.

## RF-USER-002 — Consulta cadastral

O usuário informa:

- CPF;
- data de nascimento.

O sistema consulta um serviço cadastral simulado utilizando personas
fictícias.

Quando houver correspondência, o serviço retorna o nome completo.

Durante a consulta:

- os campos envolvidos devem permanecer bloqueados;
- o usuário não poderá alterar os valores enquanto a requisição estiver
  em processamento.

Após a consulta:

- os campos devem ser desbloqueados;
- campos preenchidos automaticamente devem permitir correção manual.

## RF-USER-003 — CPF

O CPF:

- é obrigatório;
- deve possuir 11 dígitos;
- deve existir na base fictícia de personas;
- deve corresponder à data de nascimento informada;
- deve ser único entre usuários cadastrados.

Nenhum CPF real será utilizado na massa oficial de testes.

## RF-USER-004 — Idade

O cadastro somente será permitido para usuários com 18 anos completos
ou mais.

A idade deve considerar dia, mês e ano de nascimento.

Datas futuras são inválidas.

## RF-USER-005 — E-mail

O e-mail:

- é obrigatório;
- deve possuir formato válido;
- deve ser único;
- deve ser comparado sem diferenciação entre maiúsculas e minúsculas;
- deve possuir no máximo 254 caracteres.

## RF-USER-006 — Senha

A senha deve possuir:

- mínimo de 8 caracteres;
- pelo menos uma letra maiúscula;
- pelo menos uma letra minúscula;
- pelo menos um número;
- pelo menos um caractere especial.

A senha nunca deve ser armazenada em texto puro.

## RF-USER-007 — Limites de campos

Limites iniciais:

| Campo | Mínimo | Máximo |
|---|---:|---:|
| Nome | 2 | 150 |
| E-mail | 5 | 254 |
| CPF | 11 dígitos | 11 dígitos |
| Senha | 8 | 72 |
| CEP | 8 dígitos | 8 dígitos |
| Logradouro | 2 | 150 |
| Número | 1 | 10 |
| Complemento | 0 | 100 |
| Bairro | 2 | 100 |
| Cidade | 2 | 100 |
| UF | 2 | 2 |

# 4. Endereço

## RF-ADDR-001 — Consulta de CEP

O usuário informa:

- CEP;
- número.

O sistema consulta um serviço de endereço simulado.

Quando encontrado, deve retornar:

- logradouro;
- bairro;
- cidade;
- UF.

## RF-ADDR-002 — Estados da consulta

Durante a consulta os campos envolvidos ficam bloqueados.

Após a conclusão, todos os campos preenchidos automaticamente devem permitir
correção manual.

O sistema deve tratar:

- CEP inválido;
- CEP inexistente;
- timeout;
- erro do serviço;
- consulta bem-sucedida.

# 5. Carrinho

## RF-CART-001 — Visitante

Não é necessário possuir conta ou estar autenticado para criar e utilizar
um carrinho.

## RF-CART-002 — Adicionar produto

Somente produtos ativos e com estoque disponível podem ser adicionados.

Quantidade inicial: 1.

Adicionar novamente um produto já existente deve aumentar sua quantidade,
não criar uma segunda linha.

## RF-CART-003 — Quantidade

Quantidade mínima: 1.

Quantidade máxima por item:

- 10 unidades; ou
- estoque disponível;

prevalecendo o menor valor.

## RF-CART-004 — Alteração de quantidade

O usuário poderá:

- incrementar;
- decrementar;
- informar quantidade diretamente.

O botão de decremento deve ficar indisponível quando a quantidade for 1.

A remoção deve ocorrer por ação explícita.

## RF-CART-005 — Estoque

Adicionar produto ao carrinho não reserva estoque.

O estoque deve ser revalidado:

- ao alterar quantidade;
- ao iniciar checkout;
- imediatamente antes da criação do pedido.

## RF-CART-006 — Preços

Subtotal do item:

preço unitário × quantidade.

Subtotal do carrinho:

soma dos subtotais dos itens.

Os cálculos devem ser realizados pelo backend.

Valores enviados pelo frontend não são fonte confiável para cálculo do
pedido.

## RF-CART-007 — Alteração de preço

O carrinho não congela o preço.

Caso o preço seja alterado antes do checkout, o usuário deve ser informado
sobre a alteração.

## RF-CART-008 — Produto indisponível

Caso um produto presente no carrinho seja posteriormente desativado:

- ele permanece visível;
- deve ser identificado como indisponível;
- checkout fica bloqueado até sua remoção.

## RF-CART-009 — Autenticação

O carrinho pode ser montado sem autenticação.

Para iniciar o checkout, o usuário deve realizar login ou cadastro.

O carrinho deve ser preservado após autenticação.

## RF-CART-010 — Merge

Caso o usuário autenticado já possua carrinho, os itens devem ser combinados.

Produtos iguais devem ter suas quantidades somadas, respeitando estoque e
limite máximo.

Ajustes de quantidade não devem ocorrer silenciosamente.

# 6. Cupons

## RF-COUPON-001 — Tipos

A V1 suporta:

- desconto percentual;
- desconto de valor fixo.

## RF-COUPON-002 — Código

O código:

- deve ser único;
- é case-insensitive.

## RF-COUPON-003 — Aplicação

O visitante pode aplicar cupom antes da autenticação.

Somente um cupom pode estar aplicado ao carrinho.

## RF-COUPON-004 — Validade

O cupom deve:

- estar ativo;
- ter atingido sua data inicial;
- não estar expirado;
- respeitar eventual valor mínimo;
- possuir utilização disponível quando houver limite.

## RF-COUPON-005 — Limite do desconto

O desconto nunca pode tornar o valor dos produtos negativo.

## RF-COUPON-006 — Consumo

Aplicar cupom ao carrinho não consome utilização.

O consumo ocorre somente quando a compra atinge o estado definido como
válido para utilização.

## RF-COUPON-007 — Revalidação

O cupom deve ser revalidado imediatamente antes da confirmação do pedido.

## RF-COUPON-008 — Frete

Cupom comum não concede desconto sobre frete.

Ordem do cálculo:

1. subtotal dos produtos;
2. desconto;
3. subtotal com desconto;
4. frete;
5. total.

O cupom aplicado deve ser preservado durante login/cadastro e posteriormente
revalidado.

# 7. Checkout

## RF-CHECKOUT-001 — Autenticação

Checkout exige usuário autenticado.

## RF-CHECKOUT-002 — Revalidação

Antes da confirmação devem ser revalidados:

- produto ativo;
- estoque;
- preço;
- cupom;
- endereço;
- frete.

Mudanças relevantes devem ser apresentadas ao usuário.

## RF-CHECKOUT-003 — Endereço

O usuário poderá selecionar endereço cadastrado ou cadastrar novo endereço.

## RF-CHECKOUT-004 — Frete

A V1 possuirá serviço de frete simulado.

Modalidades iniciais:

- Econômico: 7–10 dias úteis;
- Padrão: 3–5 dias úteis;
- Expresso: 1–2 dias úteis.

Valores poderão variar conforme a região simulada do CEP.

# 8. Pagamentos

## RF-PAY-001 — Métodos

A V1 suporta:

- cartão;
- PIX.

Boleto e transferência bancária convencional ficam fora do escopo.

## RF-PAY-002 — Cartão

O sistema deve validar dados estruturais do cartão antes de enviar a
transação ao simulador.

A massa de testes utilizará cartões fictícios.

O simulador poderá produzir:

- APPROVED;
- DECLINED;
- TIMEOUT;
- ERROR.

O sistema não deve armazenar CVV nem número completo do cartão.

## RF-PAY-003 — PIX

PIX será processado por serviço simulado independente.

Fluxo:

1. criação da transação;
2. retorno de identificador;
3. estado PENDING;
4. simulação da transação bancária;
5. notificação ao e-commerce;
6. atualização do pagamento/pedido.

O serviço deve permitir cenários de:

- pagamento aprovado;
- expiração;
- atraso;
- timeout;
- notificação duplicada;
- erro.

## RF-PAY-004 — Tentativas

Falha de pagamento não cria automaticamente outro pedido.

Um pedido pode possuir múltiplas tentativas de pagamento.

Máximo inicial: 3 tentativas.

Após exceder o limite:

- pedido é cancelado;
- reservas existentes são liberadas;
- nova compra exige novo pedido.

## RF-PAY-005 — Troca de método

Enquanto não houver pagamento aprovado, nova tentativa poderá utilizar outro
método.

Exemplo:

Cartão recusado → PIX.

## RF-PAY-006 — Pagamento único

Depois que uma tentativa for aprovada, nenhuma outra tentativa do mesmo
pedido poderá ser aprovada.

O sistema deve impedir cobrança duplicada.

# 9. Pedidos

## RF-ORDER-001 — Status

Estados iniciais do pedido:

- AWAITING_PAYMENT;
- PAID;
- PROCESSING;
- SHIPPED;
- DELIVERED;
- CANCELLED.

Estados iniciais do pagamento:

- PENDING;
- APPROVED;
- DECLINED;
- EXPIRED;
- REFUNDED.

## RF-ORDER-002 — Snapshot

Os itens do pedido devem preservar:

- product_id;
- nome do produto;
- SKU;
- preço unitário;
- quantidade;
- subtotal.

Alterações futuras no cadastro do produto não podem modificar pedidos
anteriores.

## RF-ORDER-003 — Atomicidade

Operações críticas de criação de pedido, alteração de estoque e registro de
pagamento devem utilizar transações quando necessário para impedir estados
parcialmente persistidos.

# 10. Massa de testes

O projeto possuirá base documentada de personas e endereços fictícios.

Nenhum dado pessoal real deve fazer parte da massa oficial.

Devem existir personas específicas para cenários como:

- adulto válido;
- usuário que completa 18 anos hoje;
- usuário que completa 18 anos amanhã;
- CPF inexistente;
- CPF/data de nascimento incompatíveis;
- CPF já cadastrado.

Também existirão endereços fictícios destinados a:

- consulta válida;
- CEP inexistente;
- diferentes regiões de frete;
- respostas incompletas;
- falhas simuladas.

---

# 11. Bug Lab

Defeitos intencionais serão habilitados através de feature flags.

Exemplo:

BUG_SHOW_INACTIVE_PRODUCTS=false

Cada bug deve possuir:

- ID;
- título;
- requisito relacionado;
- flag;
- pré-condições;
- passos para reprodução;
- resultado esperado;
- comportamento defeituoso;
- teste associado.

Por padrão, todas as flags devem permanecer desabilitadas.

A aplicação sem flags de bug habilitadas representa o comportamento correto
definido por esta especificação.

## PMF-021
Ativação de conta por token.

Após concluir o cadastro:

- a conta deve ser criada inicialmente como não verificada;
- o sistema deve gerar um token de ativação único;
- o token deve ser enviado ao e-mail informado no cadastro;
- o usuário deve acessar o link de ativação para validar a conta;
- o token deve possuir prazo de expiração;
- um token utilizado não poderá ser reutilizado;
- deve ser possível solicitar um novo token após expiração;
- a emissão de um novo token deve invalidar o anterior.

## PMF-022
Recuperação de senha por token temporário.

O usuário poderá solicitar recuperação de senha através do e-mail cadastrado.

O token deverá:

- ser único;
- possuir prazo de expiração;
- permitir somente uma utilização;
- ser invalidado após alteração da senha;
- ser invalidado quando um novo token de recuperação for emitido.

### Estratégia de testes de e-mail

Para automação e CI, o projeto deverá utilizar um servidor SMTP local/fake,
permitindo capturar e inspecionar mensagens de forma determinística.

Serviços de e-mail temporário poderão ser utilizados opcionalmente para
testes manuais de integração com envio externo, sem constituir dependência
da suíte automatizada.
